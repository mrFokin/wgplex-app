# wgplex-app

Wgplex.app — меню-приложение macOS, клиент публичного API движка `wgplex` (отдельный репозиторий `mrFokin/wgplex`, локально `../wgplex`). Приложение ничего не меняет в системе само: всё через JSON-RPC 2.0 по unix-сокету `<prefix>/var/run/wgplex.sock`.

## Источник истины

- `docs/design.md` — дизайн приложения и план этапов A0–A5. Код ему следует.
- Контракт API — `docs/api.md` **движка** (появится в M3). Клиент (A1) пишется по нему, а не по Wirefork. «design wgplex N» — раздел N `docs/design.md` движка.
- Отклонение от дизайна — только после согласования с пользователем; правка `design.md` идёт в той же ветке, что и код.
- План этапа — `docs/plans/a<N>-<slug>.md` в ветке этапа: задачи, «Ход работы». Оркестратор отмечает в нём пройденные шаги.
- Вход A1 — текст для сессии `wgplex-app` из «Хода работы» M3 движка (версия движка, `api_version`, что добавлено).

## Принципы

- KISS: никаких абстракций (протоколов, реестров, обёрток) на будущее — только то, что нужно в текущей задаче.
- Без сторонних зависимостей. Swift Package, macOS 13+, режим языка Swift 6.
- Нет привилегированного кода и нет чтения конфига движка: приложение — только клиент API.
- Логика (клиент, представление статуса, вычисление уведомлений) — в `WgplexKit`, покрыта XCTest без сети и root (фейковый сервер API); `Wgplex` — тонкий слой AppKit/SwiftUI.
- Приватные ключи не попадают в логи и тестовые фикстуры (ключи в API и так не отдаются).
- Идентификатор приложения — `io.github.mrfokin.wgplex`. Не путать с Wirefork.

## Структура

```
Sources/WgplexKit/   логика: клиент API, модели статуса, уведомления
Sources/Wgplex/      приложение: NSStatusItem, окно
Tests/WgplexKitTests/
docs/                design.md, планы этапов (на русском)
```

Файлы создаются тогда, когда в них появляется код.

## Проверки

- `make check` — `swift build` и `swift test`. Зелёный перед каждым коммитом.
- GUI-проверки (меню, окно, автозапуск, уведомления) — шаги пользователя из плана этапа.

## Система

- На хосте агенты не запускают `sudo` и не меняют сетевые настройки, launchd и объекты входа (включая `SMAppService.register` при ручных запусках).
- Живой обмен с демоном — только если пользователь запустил движок сам.
- Проверки с `sudo` и движком — только в одноразовой VM tart через `../wgplex/scripts/vm.sh` (клоны `wgp-check-*`, правила — `CLAUDE.md` движка). Шаги с GUI-диалогами в VM — за пользователем.

## Git

- Работа в ветках `a<N>-<slug>`. Коммитить можно без подтверждения после зелёного `make check`.
- Слияние в `master` — если: `make check` зелёный на результате слияния; у `reviewer` нет блокеров, замечания исправлены или записаны в «Ход работы»; ручная проверка из плана пройдена; нет конфликтов. Иначе — остановиться и спросить.
- Создание GitHub-репозитория, push и релизы (тег, `gh release`, cask в tap) — только после одобрения пользователя.
- Коммиты — conventional commits: префикс на английском, описание и тело на русском (`feat(kit): клиент API`), с завершающей строкой `Co-Authored-By`.
- Комментарии в коде и README — на английском; тексты меню и окна — на русском (решение пользователя, A2, design 4); `design.md`, планы и коммиты — на русском.

## Сессии

| Сессия | Что делает |
|---|---|
| Дизайн | правки `design.md` вне этапов. Код не пишет |
| Оркестратор этапа | одна сессия на этап: план, агенты, сведение, «Ход работы», слияние |

Сессии `wgplex`, `wgplex-app` связаны через документы и пользователя, без прямых сообщений. Вопрос дизайна во время этапа — пользователю.

## Мультиагентный процесс

Оркестратор делит этап на задачи, составляет план этапа и согласует его с пользователем (сначала план, потом код), запускает агентов, сводит результат.

| Агент | Модель | Роль |
|---|---|---|
| `swift-dev` | opus | реализация Swift-кода |
| `test-dev` | sonnet | XCTest по `design.md` и `docs/api.md`, не глядя в реализацию |
| `reviewer` | opus | ревью диффа (только чтение) |
| `Explore`, `Plan`, `general-purpose` | встроенные | поиск, исследование, механическая работа; `model` передаётся при запуске |

Цикл задачи: оркестратор фиксирует план → `swift-dev` вводит сигнатуры → `swift-dev` пишет реализацию, `test-dev` параллельно тесты (файлы не пересекаются) → `reviewer` проверяет дифф → слияние по условиям из «Git». Пишущие агенты работают в отдельных worktree. Брифы узкие; `make check` — командой, а не агентом.

## Ответ оркестратора

Каждый ответ оркестратора пользователю заканчивается блоком:

```
Дальше:
- от вас: <решение | ручной шаг (что и где запускать) | ничего>
- в другую сессию: <готовый текст для вставки | —>
- следующий шаг: <что оркестратор сделает после ответа>
```
